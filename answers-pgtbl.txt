Inspect page table

Each PTE has a physical page number in bits 10 and up, and flag bits in
bits 0-9: V=0x01 valid, R=0x02 read, W=0x04 write, X=0x08 execute,
U=0x10 user-accessible, A=0x40 accessed, D=0x80 dirty.

va 0x0     pte 0x21FCD45B  perm 0x5B (V R X U A)
   Text (code), first page. Executable and readable from user mode, not
   writable, so the program cannot overwrite its own code. A is set because
   the CPU has fetched instructions from this page.

va 0x1000  pte 0x21FD201B  perm 0x1B (V R X U)
   Text (code), second page. Same permissions as above. A is not set
   because this page has not been accessed yet.

va 0x2000  pte 0x21FD1417  perm 0x17 (V R W U)
   Data (global variables). Readable and writable from user mode, not
   executable. Not accessed yet, so A and D are clear.

va 0x3000  pte 0x21FD1007  perm 0x07 (V R W, no U)
   Stack guard page. The user bit is clear, so if the stack overflows
   into it, the access causes a page fault instead of silently
   corrupting memory.

va 0x4000  pte 0x21FD1CD7  perm 0xD7 (V R W U A D)
   User stack. Readable and writable from user mode. A and D are set
   because the program has already read and written it.

va 0x5000 - 0x9000   pte 0x0
   Not mapped (valid bit is clear). The process has no memory here.

va 0x3FFFFF6000 - 0x3FFFFFD000   pte 0x0
   Not mapped. This is unused space just below the trapframe (it is where
   the USYSCALL page will be mapped once that part of the lab is done).

va 0x3FFFFFE000  pte 0x21FC94C7  perm 0xC7 (V R W A D, no U)
   Trapframe. Stores the user registers when a trap occurs. Kernel-only
   because U is clear. A and D are set because the kernel has written it.

va 0x3FFFFFF000  pte 0x2000184B  perm 0x4B (V R X A, no U)
   Trampoline. The code that switches between user and kernel mode on
   traps. Executable but not writable, and kernel-only because U is
   clear. It is mapped at the top of every address space.



vmprint: leaf pages

va 0x0, 0x1000  (R X U)
  Text (code) pages of pgtbltest. Allowed: user mode can read and execute
  them. Not allowed: writing, so the program cannot overwrite its own
  code. These are the same pages as perm 0x5B / 0x1B in print_pgtbl
  (vmprint just doesn't print the A bit).

va 0x2000  (R W U)
  Data. Allowed: reading and writing from user mode. Not allowed:
  executing, which stops injected data being run as code. Same as perm
  0x17 in print_pgtbl.

va 0x3000  (R W, no U)
  Stack guard page. The kernel could read and write it, but user mode
  has no access, so a stack overflow causes a page fault instead of
  silently corrupting the data below. Same as perm 0x7 in print_pgtbl.

va 0x4000  (R W U)
  User stack. Allowed: reading and writing from user mode. Not allowed:
  executing. Same as perm 0xD7 in print_pgtbl (A and D are set because it
  has been used).

va 0x3FFFFFE000  (R W, no U)
  Trapframe, where the user registers are saved on a trap. Only the
  kernel can touch it; user mode cannot access it at all. Same as 0xC7
  in print_pgtbl.

va 0x3FFFFFF000  (R X, no U)
  Trampoline, the code that switches between user and kernel mode. It
  can be read and executed but not written, and it is not accessible
  from user code. It is mapped at the top of every address space. Same as
  0x4B in print_pgtbl.

Non-leaf entries (no letters) point to the next-level page table, so they
are not memory the program uses directly. Unmapped pages seen in
print_pgtbl do not appear in vmprint because their PTE is 0.

Speed up system calls: which other system calls could use the shared page?

Any system call that only returns a value the kernel already knows, and
that the process is allowed to see, could be served from the shared
page. Examples:

1. uptime(): the kernel's timer interrupt handler (clockintr) increments
   the global "ticks" counter. If it also copied ticks into a field of
   struct usyscall, the user-level uptime() could just read that field
   instead of trapping into the kernel. The cost is one extra memory
   write per tick, and the value can be up to one tick out of date,
   which is the same precision as the system call itself.

2. Per-process values that rarely change, such as the process's own
   size (sz) or its pid, could be stored and updated only when they
   change (for example in growproc), so reading them is free.

Why this is safe: the page is mapped PTE_R | PTE_U only, so user code can
read it but not modify it, and it contains nothing secret that the system
call would not have returned anyway.

Limits: it only helps calls that merely read data. Calls that change
kernel state (fork, write, sbrk, kill) or need the kernel to check
permissions still have to trap into the kernel. Also, every extra field
must be kept up to date by the kernel, and the whole structure has to fit
in the one page.
